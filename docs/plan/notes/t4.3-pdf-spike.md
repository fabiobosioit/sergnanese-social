# T4.3 spike: federation calendar PDF layout

Date of spike: 2026-11-24. Input: one real sample (2 pages, kept outside the repo, gitignored; never commit it or its text). Method: PDFKit only (`PDFDocument`, `PDFPage.string`, `PDFPage.selection(for: NSRange)` one character at a time, `PDFSelection.bounds(for:)`, `PDFPage.attributedString`, `PDFSelection.selectionsByLine()`), characters grouped into runs on the same baseline with a gap under 6 pt. The signatures were checked in the SDK headers (`PDFPage.h`: `selectionForRange:`, `attributedString`; `PDFSelection.h`: `boundsForPage:`, `selectionsByLine`). This note has no real names or addresses; the synthetic fixtures in `Tests/Fixtures/pdf/` use invented ones and copy the numbers below.

## Summary

1. The sample is regular and machine-made (PDFium output, embedded TrueType subsets, real text, no scan). A positional parser is feasible. Sonnet-level heuristics are enough for this layout; the risk is a different layout from another league or phase, so every unknown must end in a flagged staging row, never a guess.
2. **Do not parse `page.string` by lines.** PDFKit joins cells of one row with a space or a newline in a way that depends on the file (see "PDFKit behaviour"). Read per-character bounds, cluster them into cells, and work on coordinates.
3. Page 1 has the matches (home, away, matchday number, date) but **no time and no ground**. Page 2 has, per club, a ground, an address, a usual kick-off time and a usual day. Time, ground and day of a match come from the home club's row on page 2.
4. Names differ between the pages (page 1 short, page 2 long with legal suffixes). A normalisation rule matched all 9 clubs of the sample uniquely (below).
5. Every date on page 1 is a Saturday. Clubs whose page 2 day is `Domenica` play one day later (inference, to confirm with the user; flag those rows).

## Page geometry (PDF points, PDFKit coordinates: origin bottom-left, y grows upward)

Both pages: A4 landscape, 841.92 x 595.32, rotation 0. Bounds are PDFKit selection bounds: `minY` is the bottom of the text box, `height` is about 1.21 x font size for body text. Use the vertical centre (`midY`) to group rows; the baseline is not exposed.

Match cell (a single logical line): `HOME- AWAY ` where the hyphen glyph sits exactly on the column axis. **Home name is right-aligned and ends at the axis; away name is left-aligned and starts at axis + 7.3** (after the hyphen and a space). The "- " is its own text run at size 6.6 (names are 7.44). The away name carries a trailing space. Consequences:

- Split a cell at the hyphen whose x is within 1 pt of a column axis, not at the first "-" in the string (names can contain dots, digits, "Sq.B"; a hyphen inside a name was not seen but cannot be excluded). Home x1 is about 143.2 and away x0 is about 150.5 in column 1.
- A bye is `Riposo- <club>` (the word Riposo takes the home position). Treat it as "club rests", not as a match.
- Cell text widths range from 47 to 181 pt, so cells never cross the column midpoint (axis +/- 135).
- The date text is `A. dd/mm/yyyy` with leading zeros. "A." is presumably "andata". The spring phase probably uses "R." (ritorno); not seen, so any other prefix letter must be accepted but flagged.
- Matchday number comes from the "GIORNATA n" header centred over the same column and band. 9 headers, 9 dates, 45 lines (36 matches, 9 byes) in the sample.

The ground string is "<ground name> - <town>" in one cell, sometimes with a second " - " (town twice) or "FRAZ."/"LOC." suffixes. Keep it whole as the venue; do not try to split it.

## PDFKit behaviour seen

- `PDFPage.string` order is the drawing order of the file, not reading order. In the real file: logos and title, then per band the three headers, the three dates, then the matches column by column (column 1 top to bottom, then column 2, then column 3), then the next band. Page 2 is written column by column (header, then 9 cells), not row by row.
- Newlines: in the real file the three headers of a band, and the three dates, are separated by `\n`; match lines are separated only by their trailing space (`"HOME- AWAY HOME- AWAY"`), with no newline. A line-based parser would break. In the synthetic fixtures (CoreGraphics output) the same items come out with a space or a newline between them in a different pattern, which is one more reason to ignore the string and use coordinates.
- `selectionsByLine()` on the real page 1 gave 67 selections (2 images, 2 title lines, 9 headers, 9 dates, 45 match lines): one per cell, a convenient unit, but the line grouping is the producer's, so on other files cells may merge. The per-character grouping above does not depend on it.
- Per-character `selection(for:)` works on every glyph and the space characters have bounds of their own (a space between two far apart cells can bridge them: break runs on a gap above 6 pt, not on the space character).
- `attributedString` reports font Helvetica for every run (PDFKit substitutes the embedded fonts) but the real point sizes: 29.88 (title), 16.56, 9.96 (headers), 7.44 (match lines and dates), 6.6 (the "- " separator), 9.0 (page 2 body), 12 and 20.04 (page 2 titles). Colours are readable too (title magenta, header text white, body black). Size could be used to tell headers from body without relying on geometry.
- The document has no text metadata worth using (title absent, producer PDFium, creation date only).

## Name matching between pages

Rule that matched all 9 clubs of the sample, each to exactly one table row: normalise both names (upper-case, replace the word `S.` with `SAN`, drop every character that is not a letter or digit), then a page 1 name matches a page 2 row when the normalised long name **starts with** the normalised short name. Cases handled: legal suffixes added on page 2 (`SSD A RL`, `S.P.A.`, `A.S.D.`), `Sq.B` against `sq.B`, `S.` against `SAN`. Needs a guard: zero matches (club missing on page 2) or two or more matches (one short name being the prefix of another) must not pick one silently; mark the row "venue unknown" or "ambiguous" for the staging review. The fixture `calendar-missing-club.pdf` covers the first case.

## What the parser can fill and what stays flagged

| Staging field | Source | Certainty |
|---|---|---|
| Home, away | page 1 cell | high; flagged when the hyphen is not on a column axis |
| Matchday label | "GIORNATA n" | high |
| Date | matchday date, +1 day if the home club's page 2 day is Domenica | medium: confirm the Sunday rule with the user |
| Time | home club's page 2 Orario | medium: a usual time, not per match; federation can change single matches |
| Venue | home club's page 2 Campo / Località (and Indirizzo) | medium; flagged if no row |
| Our team side | club name contains "SERGNANESE" (normalised) | high; flagged when none of the 9 clubs matches |
| Category and girone | title (page 1/2) and "FASE ... - GIRONE X" | high; the category is a free string and is not in the app's category list as such, so the user must map it |
| Byes ("Riposo") | page 1 | not a match: skip, do not stage |

## Differences between the synthetic fixtures and the real file

- Fonts: the real file uses three embedded families; the fixtures use Helvetica and HelveticaNeue-CondensedBold, so text widths differ (the fixtures' names are shorter, the title is a bit wider). Heights are matched by vertical centre, not by box.
- Newline pattern in `page.string` differs (see above). Tests must not depend on it.
- Geometry (axes, pitches, band positions, column x, row spacing) is copied from the measurements above to within 0.3 pt.
- Names, grounds, addresses, club numbers are invented. The fixtures keep one of each quirk: long vs short name, `S.`/`SAN`, `Sq.B`/`sq.B`, a Sunday club, a name ending in a digit year.
